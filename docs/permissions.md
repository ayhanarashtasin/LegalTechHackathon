# Permissions — Steps 2–11 prototype

Demo accounts authenticate with a 30-minute bearer session. Each request reloads active role assignments from MongoDB; browser-supplied roles are ignored. Login and session access in `NODE_ENV=production` require `STAFF_LOGIN_ENABLED=true`, while the quick-fill credential endpoint stays disabled. These are fictional accounts only, not a public identity system.

| Operation | Current server permission |
| --- | --- |
| Submit generic application | DLAO officer, case support, or helpline agent; assigned office becomes record owner |
| Submit assisted UDC intake | UDC operator only, through `POST /api/assisted`; applicant, helper, translator, and typist provenance plus consent and safe contact are required |
| Reopen/correct assisted intake | Only the submitting UDC worker, while pending review and within the demo 24-hour window; limited statement/confirmation snapshot only, with versioned corrections and human conflict choice |
| Read application status/IDs | Owning-office DLAO officer or case support |
| Accept application and create Case ID | Owning-office DLAO officer, with recorded reason |
| Record representation, facts/corrections, safe contact, consent | Owning-office DLAO officer; corrections and consent require an attestation |
| Read fact history and audit | Owning-office DLAO officer |
| Read case summary | Owning-office DLAO officer/case support, or actively assigned panel lawyer |
| Read standard document metadata | Owning-office DLAO officer/case support |
| Upload fictional text document and review/approve cited briefing | Owning-office DLAO officer only; standard `.txt` content is stored as a version, excluded from general metadata reads, and cited from readable source lines only |
| Record restricted evidence | Owning-office DLAO officer. It is classified at first upload, so no ordinary-access window opens, and only the uploader is granted. Sensitivity cannot change on later versions. Evidence must be a harmless synthetic placeholder |
| Read restricted document metadata | Owning-office DLAO officer/case support **and** an explicit per-user grant, **or** the named responsible receiving DLAO of an open referral that includes it. Office role alone is never enough. Every open and every denial is appended to `EvidenceAccessLog`, which is kept outside the audit chain so reads do not change record versions. Ungranted staff see only a redacted placeholder |
| Read restricted-evidence access log | Owning-office DLAO officer; document labels only where that officer is granted |
| Send referral package | Owning-office DLAO officer, accepted case only, one waiting referral at a time. The receiver must be an active receiving DLAO in another office. Restricted evidence goes only if the sender holds a grant and records why sharing is necessary. Sending is blocked while a jurisdiction escalation is open and bound by any recorded routing decision |
| Read referral package | Receiving DLAO in the receiving office. Restricted labels show, and documents open, only for the named responsible actor while the referral is open (not after return). Safe-contact rules are included; the contact number is not |
| Acknowledge, accept, or return referral | Any active receiving DLAO in the receiving office; accept and return need a reason. The acknowledgement task closes automatically. Returns count toward the escalation threshold |
| Jurisdiction escalation | System only, after two returned transfers (demo threshold). It creates an open routing-decision task and never chooses the office |
| Record routing decision | Owning-office DLAO officer, with reason (who holds this authority is pending legal verification). It closes the escalation; `REFER` binds later referrals to that office, and `RETAIN` blocks referral until a new decision |
| Referral acknowledgement overdue | Server timer (`SYSTEM`): after the deadline passes unacknowledged, it creates one follow-up task and audit event per referral |
| Submit 16699 voice-simulation intake (`POST /api/voice/intakes`) | Public, no sign-in; strict field schema, 20 submissions per IP per 10 minutes. Response contains the new Application ID and a one-time 6-digit status PIN (read out on the call). A complaint goes to the DLAO queue; an information/advice request goes to the helpline workspace instead. Provenance is set by the server, and writes are attributed to a disabled automated-channel account |
| Record a 16699 advice callback outcome (`POST /api/applications/:applicationId/advice-outcome`) | Helpline agent of the owning office only, once per request, with the information given. "Formal legal aid needed" requires the applicant name and district (NID optional, format-checked) and moves the same record to the DLAO queue; entries are staff-entered facts and audited |
| Transcribe one spoken answer (`POST /api/voice/answers`) | Public, rate-limited, max 2 MB of audio, and only for questions already asked. The audio is transcribed and discarded, never written to disk or the database. The API key stays server-side, and the reply holds only the transcript plus values for approved fields. Returns 503 when voice AI is off |
| Attach the full call recording (`POST /api/voice/intakes/:applicationId/recording`) | Public, rate-limited, max 8 MB of audio, once per application, within 15 minutes of submission, and only with that submission's one-time status code (`x-lookup-code`). An identical retry returns success without a second recording or audit event. Audited with size and SHA-256 |
| Play the call recording / read the voice transcript | Owning-office DLAO officer only. Every call is recorded under the greeting's notice (project decision 2026-09-23); no opt-out is offered |
| AI-extracted answers | The model only proposes values for questions already asked; the browser and then the server re-check each one against the same script. The model cannot set provenance, confirmation, or any role |
| Log contact attempt (including simulated unknown-person answer) | Owning-office DLAO officer; an unknown-person outcome returns neutral wording only and creates a safer follow-up task |
| View own cases and request a lawyer change | Authenticated citizen linked to the Application by `citizenUserId` or applicant `personId`; request requires an accepted Case and accepted active lawyer. Other citizens receive 404. Open or approved requests block duplicates until review/replacement finishes; DLAO review and reassignment remain separate actions |
| Manage hearing/next step, offer assignments, schedule mandatory updates, and review applicant change requests | Owning-office DLAO officer on an accepted Case; each consequential action records a reason and audit event, and approving a change request does not reassign by itself |
| View/accept/decline panel assignment; read assigned Case and standard documents | Active panel lawyer in the Case's office, for their own pending/accepted assignment only; pending offers expose no case plan or documents; restricted evidence is never included |
| Submit scheduled progress update | The assigned panel lawyer on an active accepted assignment; due reports are marked late, and overdue items create a DLAO follow-up task |
| Review temporary new-assignment hold | DLAO officer in the configured demo reviewer office; may lift or continue with a reason; existing assignments remain active and reassignment is separate |
| Record and read stage-based payment status | Owning-office DLAO officer for accepted or reassigned panel work; latest status per stage and full event history remain visible, with no money movement or automatic recovery |
| Create/view related-incident group | Owning-office DLAO officer; only accepted Cases from the same office, linked without merging; individual instructions, outcomes, and confidentiality remain on their own Cases |
| Share/read related-incident evidence | Owning-office DLAO officer; only an existing readable `STANDARD` document from a group member, linked by its existing document ID and audited on member records. Restricted evidence cannot be shared |
| View duplicate suggestions/review a pair | Owning-office DLAO officer; deterministic same-office ranking from normalized names, exact contact number, date of birth, and district. The score is not a probability or identity proof; review requires a reason and records remain unchanged |
| Run/read multi-agent triage and record officer decision | Owning-office DLAO officer. Structured Groq inputs exclude names, contact details, DOB, free-text complaints, and document content; invalid/unavailable model output uses the deterministic fallback. Every component requires human review; decision is reasoned/audited and does not change priority, route, eligibility, or outcome |
| Read daily queue, reasons, and routine report | Owning-office DLAO officer or case support; referral-waiting and lawyer-update-overdue flags are live |
| Override priority recommendation | Owning-office DLAO officer, with reason and immutable audit event; recommendation remains visible |
| Read redacted reconstruction history | Owning-office DLAO officer or case support; event action/role/time and integrity only, not private reasons or fact text |
| Helpline status lookup | Owning-office helpline agent with exact ID, one-time displayed code, explicit human caller-verification attestation, and an active permitted phone or in-person profile. Returns generic status, hearing date, and next step only; logs a ContactAttempt and audit event on the same Application |

Receiving DLAOs see only referral packages sent to their office, never the full record, facts, audit, or task list. All other roles have no protected-record API permissions yet. UDC cannot use the generic submit route, read full records/facts/documents, or retain unrestricted ownership after submission. Helpline can only use the bounded status lookup. An unassigned lawyer cannot browse cases; no lawyer receives restricted evidence merely from assignment. The public voice intake can create a record but never read one. Unknown contact safety means disclose nothing; storing a safe-contact profile does not itself authorise outbound contact. Older records made before Step 6 have no lookup code and cannot use this lookup.

Offline drafts are AES-GCM encrypted with a local passphrase in IndexedDB, not in the static service-worker cache. The browser verifies the ciphertext hash before decrypting/syncing, deletes synced drafts, and clears the draft store on logout. This protects ordinary shared-device handoff only when users actually sign out and keep the passphrase private; browser storage or device compromise is not a substitute for a deployment policy. The service worker caches app-shell/static files and excludes `/api/` and `/health`. Uploaded content and AI briefing are officer-only server reads; the model may summarize cited fictional excerpts but cannot approve a briefing or make a legal decision.

The lookup code is stored only as a SHA-256 hash and displayed only in the submission response. It is **not identity proof**. The demo requires a human attestation but cannot verify that the human followed a real procedure; the law team must approve caller verification and wording before any real service use. No helpline note store is added: the lookup appends to the existing ContactAttempt and Application audit history.

Role and document denials are tested through direct HTTP calls. Routine denied reads are not yet audit-logged; Step 13 must review this with privacy and abuse-monitoring needs. Application audit history covers state changes, not every read.
