# Prototype threat model

Reviewed 2026-09-23 for the current local/demo implementation. This is a bounded engineering threat model, not a production security assessment. The system is a React SPA and Express API backed by MongoDB Atlas or a local MongoDB. Provider actions are authenticated with short-lived bearer sessions; the browser calls relative `/api` URLs through the development proxy or a configured API origin when separately hosted. Data must be fictional. Production staff sign-in is disabled by default and requires an explicit server setting. No real 16699 telecom, SMS, email, push notification, government identity, or payment integration is present.

## Trust boundaries and assets

- Citizen, representative, helper, and uploaded text are untrusted input. AI output and client timestamps are also untrusted.
- The browser/device and network are outside the server trust boundary. The API validates role, office, assignment, schemas, workflow transitions, and document access before reads or writes.
- Sensitive assets include identity/contact details, safe-contact preferences, complaint and safety facts, restricted evidence, consent/provenance, mediation drafts/signatures, session tokens, offline drafts, and the audit history.
- Groq is an external processor when a live AI feature is enabled. The deployment operator controls credentials; no API key belongs in the client bundle.
- Database administrators and a compromised API host are privileged threats. Hash chains and signatures do not protect against a privileged actor rewriting both data and verification records.

## Threat scenarios

| Threat / asset | Attacker capability and controls | Detection and recovery | Residual risk |
| --- | --- | --- | --- |
| Shared device; cached or visible case data | A later device user may inspect the prior session. The token is held in React memory, not local/session storage; logout clears the local encrypted-draft database; the service worker caches the static shell only; API responses are `no-store`. | Logout attempts to purge drafts and warns if local clearing fails. Audit events cover consequential server actions. | A user who inherits an unlocked active tab can act as that user until logout/session expiry. Browser history and screenshots are outside app control. Static-host security headers must be configured separately. |
| Stolen or unsafe phone | A thief may use a browser left signed in or inspect device storage. No real SMS/contacting flow exists. Offline drafts/signature packets are encrypted in IndexedDB and require the local passphrase to open; provider bearer sessions expire after 30 minutes and logout revokes the server-side session. | Failed/unauthorised reads are denied; restricted evidence access attempts are logged. User should sign out and secure the device. | No MFA, remote device wipe, or administrator session-revocation workflow. An unlocked browser remains usable; passphrase strength and device compromise matter. |
| Malicious/untrusted caller or representative | Caller may lie, submit prompt injection, or claim another person's authority. Inputs are bounded and schema-validated; reported/translated/AI-inferred facts retain provenance; representation and applicant confirmation are separate; humans decide consequential actions. | Corrections append history; intake and decisions are audited; human review handles uncertainty. | The system cannot prove identity, authority, truth, or informed consent. The helpline's one-time code plus staff attestation is not identity proof. Whoever holds a fresh status code can attach one call recording (8 MB cap, 15 minutes, once, audited with its SHA-256) to that application. |
| UDC helper overreach; applicant data | A helper may attempt to read/edit unrelated records or substitute their own contact. Server checks the authenticated UDC role and office, confines correction to the actor's eligible assisted intake, and keeps helper, translator, typist, applicant, and contact ownership separate. | Mutations and conflict resolutions are audited; denied API access is covered by role-negative tests. | Coercion, shoulder-surfing, collusion, and misuse of an authorised in-person session cannot be prevented technically. |
| Weak/offline connectivity; draft confidentiality | A network interruption may cause duplicate submissions or expose a shared-device draft. Local drafts and signature retry packets are encrypted; mutation IDs make retries idempotent; sync checks record versions and presents stale conflicts for a reasoned human choice. The service worker caches no case API data. | Sync outcomes/conflicts are audited; local integrity can be checked and logout purges local drafts. | Browser storage can be cleared/corrupted, a weak passphrase can be guessed offline, and unsynced data cannot be recovered if the device is lost. There is no silent merge. |
| Duplicate replay; state integrity | A caller can replay a request or reuse an offline mutation ID. Unique indexes, transaction checks, version checks, and mutation-ID comparisons reject duplicate or changed replays; signature records bind signer, version, and hash. | Conflicts return stable errors; successful state changes create audit events. | A privileged database operator can rewrite records and the local audit chain; the chain is not externally anchored. |
| Stale offline edits; provenance | A delayed edit may overwrite a newer staff change. Optimistic version checks reject stale writes; the UI shows server and local versions and requires an explicit human choice/reason. Corrections append rather than replace facts. | Conflict and resolution actions are audited; tests exercise stale-version failure and recovery. | Conflicts are record-level rather than field-level, and human reviewers can still choose incorrectly. |
| Modified signed settlement or stolen party code | A party or operator may alter a signed document, substitute a key, or use a code delivered to the wrong person. P-256 signatures cover canonical content/hash/version; server and independent browser verification report invalid/tampered copies. Each party code is a separate 256-bit secret stored only as a hash on the server, bound to one party/draft, expiring in seven days and invalidated on replacement or use. The mediator cannot submit a party signature through the staff route and signs after both parties; CLAO applicability/certification is separately gated. | Code issue and party signing are audited without the plaintext code. Verification failure blocks certification and is visible to the reviewer. The mediator must verify the delivery route and can replace an unused code. | Whoever obtains an active code can view the approved draft and sign as that party. Codes and signatures do not prove identity, capacity, informed consent, enforceability, or commencement/territorial applicability. Database compromise can replace both content and stored public keys/signatures. No court-decree claim is made. |
| Prompt injection or unsafe AI output | Caller text, documents, or notes may instruct an AI to change roles, disclose data, or make decisions. AI has no database write or permission authority; model outputs use strict allowlisted schemas and server-side validation; evidence references are checked; workflow decisions remain human. Invalid/provider-failure output falls back or stops safely. | AI assistance/model and human review outcomes are auditable without chain-of-thought; malformed output is rejected. | Live voice processing and some document/settlement assistance send untrusted source text/audio or notes to Groq. Settlement notes rely on a mediator's identifier-removal attestation; there is no guaranteed PII detector. Provider retention/processing terms and legal basis need review before real data. Models can still produce plausible errors. |
| Leaked browser bearer token | Malware, XSS, or a person with browser access may copy a token and replay it. Tokens are random 256-bit values, stored server-side only as SHA-256 hashes, kept in memory in the SPA, expire after 30 minutes, and logout revokes the token. Production sign-in requires `STAFF_LOGIN_ENABLED=true`; the quick-fill credential endpoint stays disabled. | Access-control checks and audit events limit and reconstruct consequential actions; use logout and end the session. | A copied active bearer token works until logout/expiry. There is no MFA, refresh rotation, or per-device admin revoke. These fictional seeded accounts are not a production identity system. |
| Login brute force and request abuse | A remote user may guess demo passwords or send oversized JSON. Login allows five failures per username/source IP in 15 minutes; public voice routes are rate-limited with a bounded 4,096-IP in-memory window; request bodies are capped; IDs/enums/fields are validated; basic API hardening headers are emitted. | Rate-limited attempts receive `429`; errors avoid stack/data details. | Both limiters are process-local and reset on restart; distributed attackers can use multiple addresses. Before scaling, use a shared rate limiter. Behind a proxy, configure only trusted proxy hops; `trust proxy` is intentionally not enabled by default. |
| Status-code guessing on the public tracker | A 6-digit PIN (16699 callers, the seeded Malek case) has 10^6 values, and Application IDs are sequential. The typed tracker and the spoken status route share one per-address limit (20 per 10 minutes), and ten wrong codes for an ID string lock it for an hour on both routes, from any address; a locked ID answers the same whether or not it exists. Because the code holder may be on a shared screen or phone (a shop's number, for Malek), the public result carries progress only: no applicant name, legal matter, or lawyer name, in the API response as well as on screen. The spoken route asks whether the caller can listen privately before the PIN and speaks nothing about the case without a clear yes, and the PIN is never read back or shown. | Locked IDs answer `429 TOO_MANY_ATTEMPTS`; the caller is sent to the 16699 helpline. | A deliberate lockout also blocks the real holder for an hour. The counters are process-local and reset on restart. Code possession is not identity proof. |
| Unsafe contact / notification disclosure | Staff may attempt a channel prohibited by the active contact plan. The shared contact-attempt service rejects ordinary/success outcomes on disallowed channels; it still permits a blocked attempt or an already-occurred unknown-person answer to be logged with no disclosure and safer follow-up. Status lookup checks the profile and returns generic status only. No outbound notification/call is sent by this prototype. | Blocked attempts and lookups are recorded without sensitive disclosure; unknown-person outcomes create a safer-follow-up task. The officer must state whether anything reached the person who answered (it is not assumed), and a stated disclosure creates its own review task and an audit event; unsuccessful attempts carry a dated next attempt, so repeated tries are visible. | Safe-contact rules are only as accurate as the human-entered profile. Any future SMS/email/push integration needs a separate neutral-preview design and consent/safety review. |
| Restricted evidence access | An office user may enumerate evidence or a receiving office may exceed a referral. Standard documents are office-scoped; restricted evidence requires a named user grant or live referral responsibility; ungranted users see generic labels; each restricted read/denial is logged. | Evidence access log and negative RBAC tests provide detection; access grants/referrals can be reviewed. | Compromised authorised accounts and database administrators remain in the trust boundary; access-log integrity is not externally anchored. |

## Implemented baseline and deployment limits

- Cross-origin API access is enabled only for the exact `CLIENT_ORIGIN` configured on the server. The SPA uses same-origin relative API paths by default (Vite proxies them in development); a split deployment sets `VITE_API_ORIGIN` to the API host. No wildcard credentials are enabled.
- API responses include `no-store`; API/health responses include CSP, framing, MIME-sniffing, referrer, and permissions headers. The static SPA host/CDN must apply equivalent headers separately. TLS, HSTS, host firewalling, secrets configuration, dependency monitoring, and backups belong to Step 15 deployment and are not claimed here.
- JSON bodies are capped at 128 KB to allow bounded 50 KB text documents after JSON encoding. The server accepts only `.txt` content in the document route and applies a 50 KB UTF-8 content limit. There is no binary upload, malware scanner, or scanned-PDF parsing.
- Login throttling and scheduled follow-up jobs are process-local. Do not run multiple instances until the limiter and scheduler are moved to shared infrastructure.
- MongoDB audit hashes provide tamper evidence only while the database and hash inputs are trusted; they are not proof against a privileged database rewrite.

## OWASP Top 10 source review (2021)

This bounded source review follows the available OWASP categories; the project's referenced review playbook and finding template are absent. It is not a formal assessment or penetration test.

| Risk | Severity before public deployment | Evidence and remaining action |
| --- | --- | --- |
| A01 Broken access control | High | API routes and services enforce roles, offices, assignments, and restricted-evidence grants; negative tests cover key paths. Opt-in demo staff login uses fictional seeded accounts, not production identity; do not use real beneficiary data. |
| A02 Cryptographic failures | High | Scrypt password hashes, hashed random bearer tokens, AES-GCM offline drafts, and P-256 signatures are present. Production TLS/secrets are not configured; signatures do not prove identity or consent; audit hashes lack an external anchor. |
| A03 Injection | Low / unverified externally | Request fields and identifiers use allowlists; Mongoose queries use structured objects; React renders escaped text; Groq URLs are fixed. No dynamic scan or penetration test was run. |
| A04 Insecure design | Medium | AI cannot take final actions and the domain contains human gates. Several urgency, referral, lawyer-hold, and legal-applicability thresholds remain demo assumptions requiring policy/legal approval. |
| A05 Security misconfiguration | High | API responses have `no-store` and basic headers. The static host still needs CSP/security headers, HTTPS/HSTS, secrets configuration, and a deployment access model. |
| A06 Vulnerable components | Low / unverified externally | `npm audit --workspaces` reported zero known vulnerabilities on 2026-09-23. No SBOM or independent dependency review was produced. |
| A07 Identification and authentication failures | High | Demo login uses scrypt, 256-bit random tokens, 30-minute sessions, and throttling. There is no production identity/MFA; production staff sign-in is disabled unless explicitly enabled for a fictional public demo. |
| A08 Software and data integrity failures | Medium | Schema validation, mutation IDs, signatures, and an audit hash chain protect ordinary workflows. No external audit anchor or signed deployment/release pipeline exists. |
| A09 Logging and monitoring failures | Medium | Consequential actions and restricted-evidence access are audited. There is no centralized monitoring, alerting, incident response, or approved retention policy. |
| A10 Server-side request forgery | Low / unverified externally | No user-provided URL is fetched; AI requests target a fixed Groq endpoint. No external SSRF assessment was run. |

## Verification evidence

Security and workflow checks are in `server/src/step2.test.js`, `server/src/step9.test.js` through `server/src/step12.test.js`, and `tests/e2e/step7.spec.js` through `tests/e2e/step13.spec.js`. `npm audit --workspaces` reported zero known vulnerabilities on 2026-09-23. These automated tests use fictional data. Keyboard/browser journeys cover major flows, but no manual NVDA/VoiceOver session, external penetration test, production static-host header check, or law-team security/privacy review has been completed.
